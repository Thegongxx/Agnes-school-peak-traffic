# 校园高峰路口信号配时优化智能体

## 推荐定位

- **主赛道：** 工程设计与数字世界
- **具体方向：** 环境能源与城市系统
- **可兼选方向：** 数学计算与科研智能体（算法发现与组合优化）
- **一句话介绍：** 面向校园高峰混合交通，智能体读取路口流量和通行约束，生成可执行的信号配时候选方案，调用交通仿真进行比较，并在违反安全约束或效果不佳时修正方案。

作品目标是做一个**仿真决策助手**，不是直接接管校园道路上的真实信号灯。参赛展示以仿真和可复现数据为证据。

**本项目是全新、独立的项目，从空项目开始搭建，不依赖或复用任何以前实验的代码、模型、数据或仿真环境。**

## 最后展示出来是什么样

最终做成一个本地可运行的网页仪表板，现场从“选择高峰场景”开始，点击运行后能看到方案和仿真过程。页面可以按下面布局设计：

```text
┌ 校园路口信号配时优化 ─ 场景：课前高峰 ─ [运行优化] ┐
├──────────────┬────────────────┬────────────────────┤
│ 路口俯视动画     │ 固定方案 / 优化方案 │ AGH 执行轨迹          │
│ 车辆、排队、信号灯 │ 平均等待、最大排队    │ 读取→基线→搜索→仿真→验证│
│ 当前相位与倒计时   │ 行人等待、通过量       │ 工具输入、返回、重试    │
├──────────────┴────────────────┴────────────────────┤
│ 数据来源、配时约束、测试结果、导出对比报告                    │
└─────────────────────────────────────────────────────┘
```

这是一个软件仿真演示，不需要真实交通灯接线。现场演示从用户选场景开始，能看到 AGH 实际调用仿真工具，最后对比固定配时与优化配时。

## 需要准备什么资料

**不需要先给项目一张路口照片。** SUMO 里可以直接创建简化的十字路口、车道、信号相位和车辆路线。路口照片、卫星图或学校地图都只是可选的视觉参考，不能代替仿真器需要的路网和流量数据。

- 最好选校园内一个普通十字路口，记录早高峰每个进口方向的车辆数、转向比例和行人数量，并记录统计时间段。拍摄车辆或行人不是必需的。
- 如果暂时无法现场计数，可先用低、常态、高峰三组**合成流量**启动开发，在界面和报告里明确标注“合成数据”。
- 记录一套固定配时作为比较基线；如果现场没有可查数据，就把它设为项目自定义的仿真基线。
- 需要说明安全约束，例如相位不冲突、黄灯/全红清空时间固定、最短绿灯、行人过街时间和总周期范围。数值须由选定路口条件或项目假设给出。

## 现在从哪里开始

### 先把 AGH 跑起来

比赛要求的是 **Agnes Harness（AGH）作为智能体运行底座**，不是泛指任意一个聊天机器人。AGH 需要在核心任务里实际规划并调用仿真能力，至少形成规划、工具调用、反馈/验证三个连续步骤。代码可以在 VS Code 等编辑器里写；AGH 负责运行任务、调用注册好的仿真工具并留下可检查轨迹。

先看赛事官方交流群有没有指定 AGH 版本或统一启动方式，优先按组委会提供的环境操作。没有专用版本时，官方公开仓库目前是源码构建的开发者预览版，要求 Node.js 24.10+ 和 pnpm 10.34.5。官方给出的本地启动命令是：

```powershell
git clone https://github.com/AgnesAI-Labs/agnes-harness.git
cd agnes-harness
pnpm install --frozen-lockfile
pnpm --filter @agnes/cli build:local
node packages/cli/dist/local/agnes.mjs serve
```

启动后打开终端打印的本机地址，配置模型并创建任务。先运行 AGH 自带的单工具示例，确认能在轨迹中看到一次真实工具调用。Windows 支持需要自行验证；如果官方赛事群有可直接使用的版本，优先使用比赛提供的版本。

### 再做交通仿真

在普通代码编辑器里建立本项目，安装 SUMO，用 NetEdit 建一个单路口场景，再用 Python/TraCI 跑固定配时基线。SUMO 官方教程有 Python 控制信号灯的最小例子；先复现它，再替换成自己的流量和优化规则。

### 接入 AGH，最后补界面

把读取场景、运行基线、搜索配时、运行候选、验证结果封装成 Python 工具，并按 AGH 当前版本支持的插件或 MCP 方式接入。到 AGH 工作台中注册服务、信任并启用工具；然后从 AGH 会话启动整条流程，查看工具输入、工具结果、失败重试和最终验证轨迹。最后再做网页仪表板，把 SUMO 结果、指标对比和 AGH 轨迹展示出来。

**简明分工：** VS Code 写项目代码；SUMO 模拟车流和灯控；Python 计算候选与指标；AGH 组织工具调用、接收反馈并记录过程；网页展示结果。不是把所有代码粘进 AGH 聊天框里，也不能只用 AGH 辅助写代码后就算满足比赛要求。

## 项目解决什么问题

校园出入口、食堂周边或宿舍区路口在上课前后会出现流量变化。固定配时可能让某个方向排队过长，也可能让行人等待过久。本项目让 AGH 智能体围绕一个选定路口完成“读取场景—比较方案—仿真—验证—修正”的闭环。

**目标用户：** 校园交通管理人员、后勤部门或交通工程课程师生。

**项目边界：** 只研究一个四岔路口和少量典型场景；不连接真实信号灯，不向道路发送控制命令。

## 推荐实现方案

### 仿真环境

优先使用 **SUMO** 建一个单路口交通场景。用 Python 经 TraCI 启动仿真、设置或切换信号方案，并读取车辆等待时间、排队长度、通过量等结果。信号相位的冲突关系、黄灯和清空时间、最短绿灯时间等作为不可违反的约束。

交通需求优先采用自己对一个校园路口做的匿名人工计数；若来不及采集，就使用明确标注为“合成数据”的低流量、常态、高峰三组输入。不要把合成数据写成学校真实交通数据。

### 优化方法

先准备一个固定配时作为基线，再由确定性的 Python 搜索程序生成有限个合法候选配时并批量仿真。由仿真器算分，选出车辆平均延误较低且行人等待、各方向公平性仍满足约束的方案。

让模型负责理解任务、选择场景、组织工具调用和解释结果；让仿真器负责产生交通指标，让规则检查器负责判断相位是否合法。**不要让模型编造仿真数值，也不要只靠模型口头宣称“优化有效”。**

### AGH 里的工具

把本地 Python 仿真程序封装为 AGH 可调用的工具；推荐按 AGH 官方文档的 MCP/插件接入方式实现。工具至少包括：

| 工具 | 输入 | 输出 |
|---|---|---|
| `load_scenario` | 场景编号 | 流量、路口配置、配时约束、随机种子 |
| `run_baseline` | 场景编号 | 固定方案的延误、排队、通过量等指标 |
| `search_timing_plan` | 场景与约束 | 若干合法候选方案及搜索依据 |
| `run_candidate` | 场景编号、候选方案 | 候选方案仿真指标 |
| `verify_and_compare` | 基线结果、候选结果、约束 | 是否通过、差异、失败原因 |

实际演示时，必须从 AGH 的会话里发起任务并让它调用这些工具。只在 AGH 外运行仿真、再把结果粘贴进聊天，不能清楚证明 AGH 承担了核心任务。

## 如何满足“至少三个连续步骤”

一次可展示的 AGH 轨迹建议包括以下连续环节：

1. **任务规划：** AGH 确认路口、场景、目标指标和硬约束，选择先跑基线再优化。
2. **读取能力调用：** 调用 `load_scenario` 读取场景和约束。
3. **建立比较基线：** 调用 `run_baseline`，保留固定方案结果。
4. **生成与执行候选：** 调用 `search_timing_plan`，再调用 `run_candidate` 实际运行仿真。
5. **反馈处理与结果验证：** 调用 `verify_and_compare` 检查约束和指标；不合格时把失败原因带回搜索工具，有限次数重试；仍失败则退回基线并说明原因。
6. **生成结果：** 输出被测方案、数据来源、基线/优化指标、约束检查、失败场景和 AGH 执行记录。

这样在 AGH 轨迹里可以看见规划、多个工具调用、工具返回、基于返回结果的修正和最终验证，而不是只有一轮问答。

## 验证计划

| 测试类型 | 场景 | 预期行为 |
|---|---|---|
| 正常 | 低流量、常态流量、高峰流量 | 对比固定基线和优化方案；完整输出指标 |
| 边界 | 单方向极高流量、行人流量高、输入为零或接近容量上限 | 不突破相位和绿灯约束；标出无法同时满足的目标 |
| 失败 | 缺少某方向流量、字段格式错误、仿真工具超时、候选配时冲突 | 拒绝无效方案，解释原因；安全地返回基线或要求补数据 |

建议先把验收指标定成项目目标，而不是宣称普遍适用的交通标准：

- 所有候选配时通过相位冲突和最短/最长时间检查。
- 在常态和高峰场景中，固定随机种子重复运行后，车辆平均延误相对基线有可复现改善；可先把 **5%** 设为开发目标，实际未达到时如实报告。
- 行人等待时间和各进口道最大等待时间不超过团队预先约定的上限；若优化车辆延误导致行人等待恶化，判定为不通过。
- 报告原始输入、SUMO 配置、随机种子、基线结果和候选结果，确保评委可复跑。

具体阈值要依据你选的场景、计数数据和仿真配置确定；报告里写清假设，不把仿真结论包装成真实道路实测结论。

## 可复制到 AGH 的项目启动提示词

```text
你是“校园高峰路口信号配时优化智能体”。本项目属于工程设计与数字世界，具体方向为环境能源与城市系统。请使用当前工作区中的仿真工具，围绕一个校园路口比较固定配时与候选优化配时。

必须遵守：
1. 所有核心任务通过 Agnes Harness（AGH）执行；不要绕过 AGH 在外部直接调用仿真工具。
2. 先读取场景和约束，再运行固定配时基线，然后生成候选、运行仿真、验证结果。至少完成三个连续的任务/工具/反馈步骤，并让每一步在 AGH 轨迹中可检查。
3. 交通指标只能引用仿真工具实际返回的数据。不要编造、推测或改写成真实观测数据；缺少数据时先指出缺项，合成数据必须标为合成数据。
4. 不得违反相位冲突、黄灯与清空时间、最短/最长绿灯、总周期、行人通行等配置约束。模型给出的配时必须先经确定性规则检查，再运行仿真。
5. 仿真结果不满足约束或没有优于基线时，解释失败原因并最多重试两次；仍未通过就返回基线方案和限制说明，不要声称优化成功。

执行顺序：
A. 说明本次任务计划、场景、指标和硬约束。
B. 调用 load_scenario；如果输入不完整，停止并列出缺失字段。
C. 调用 run_baseline 获取固定配时指标。
D. 调用 search_timing_plan 生成合法候选，再调用 run_candidate 实际仿真。
E. 调用 verify_and_compare 检查硬约束并与基线比较；若失败，将具体失败原因传回搜索步骤后重试，最多两次。
F. 输出简明报告：数据来源、场景和假设、基线方案、候选方案、各指标差异、约束检查、重试/失败记录、复现方法，以及本次 AGH 工具调用清单。
```

这是启动任务的提示词，不会自动安装工具。实际运行前，需先在 AGH 中接入并启用上述仿真工具；工具名称应与实现中的名称保持一致。

## 如何开始使用 AGH

Agnes Harness 是智能体运行底座，模型是它调用的推理服务，SUMO/Python 是它调用的仿真能力。三者不是同一件东西。

1. 按赛事群或官方仓库当前说明安装 AGH，并设置模型。为减少官网规则页面和报名承诺里的模型表述不一致带来的风险，初版建议选用 Agnes 模型；若要用其他模型，先向组委会确认。
2. 在 AGH 创建项目会话，把工作目录指向本项目。
3. 把 SUMO 控制与指标计算写成本地 Python 工具，按 AGH 当前版本支持的插件/MCP方式注册、信任并启用。
4. 先在 AGH 中单独调用 `load_scenario` 和 `run_baseline`，确认工具输入输出能在 AGH 轨迹里看见。
5. 再粘贴上面的启动提示词，完整跑一遍优化闭环；保存轨迹、配置文件、仿真结果和失败场景记录。

AGH 当前公开仓库标为开发者预览版，需从源码构建；官方 README 列出的环境为 Node.js 24.10+ 和 pnpm 10.34.5，并说明 Windows/Linux 需要自行验证。先跑通 AGH 自带的单工具示例，再接入 SUMO，避免同时排查框架和业务工具两类问题。
